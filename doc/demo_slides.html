⏳

评审带宽瓶颈

高级开发者时间有限，PR 排队数小时甚至数天，成为团队交付瓶颈

ReviewPilot 用 AI 做第一轮全面初审，让人类评审者聚焦在高价值决策上

核心引擎：两阶段 AI 分析

为什么分两阶段？如果对每个 PR 都用最强模型全量分析，成本太高、延迟太大。先用快模型初筛，再用强模型针对性深度分析。

⚡ Stage 1 · 快模型

deepseek-v4-flash · 目标 < 10 秒

1

接收 PR 标题 + diff 摘要 + 变更文件列表

2

生成变更总结（中文/英文可配）

3

标记高风险文件 + 输出 risk_level 评级

4

建议 Stage 2 分析方向（如只分析 security+logic）

🧠 Stage 2 · 强模型

deepseek-v4-pro · 四类别并行 · 独立 prompt 模板

🔒

Security 安全

SQL 注入 · XSS · 敏感信息泄露 · 权限绕过 · 不安全反序列化

🧩

Logic 逻辑

空指针 · 边界条件 · 异常处理 · 死锁风险 · 状态不一致

⚡

Performance 性能

N+1 查询 · 内存泄漏 · 阻塞 IO · 不必要对象创建 · 算法复杂度

🎨

Style 风格

命名规范 · 函数长度 · 圈复杂度 · 代码重复 · 最佳实践

AST 确定性规则引擎

AI 有幻觉风险，可能漏掉确定性安全问题。AST 用 Python ast 模块解析源码为语法树，9 个 NodeVisitor 遍历节点精确匹配。AST 做"有没有"的确定判断，AI 做"危不危险"的上下文判断，两者互补。

Python · 9 条规则

规则级别类别
exec / eval 动态执行Critical安全
pickle.loads() 反序列化Critical安全
subprocess shell=TrueCritical安全
SQL 字符串拼接（f/+ 传给 .execute）Warning安全
硬编码密钥/密码Warning安全
裸 except 无异常类型Warning最佳实践
open() 无 with 语句Warning最佳实践
圈复杂度 > 15Warning风格
函数长度 > 50 行Suggestion风格

误报控制（内置于检测器）

1

已知测试值过滤

test_password / example_key / changeme 等不会触发硬编码密钥告警

2

ORM 调用识别

SQLAlchemy 的 execute() 参数化查询不会被误报为 SQL 注入

3

安全上下文字段

with open() 不会触发资源泄漏；不含 shell=True 的 subprocess 不会告警

GitHub Bot 评审全流程

从 PR 提交到评论创建，全自动 6 步链路，关键设计：后台线程处理避免 10s 超时

1

事件接收

GitHub Webhook POST → ngrok 隧道 → FastAPI → HMAC-SHA256 签名验证

Webhook 只含元数据，不含代码

2

事件路由 + 后台线程

EventRouter 解析 event_type → 路由到 AutoReviewHandler 或 CommandHandler

后台 daemon 线程 · 主线程立刻返回 200

3

数据拉取

JWT → Installation Token → GitHub API 主动拉：PR 详情 + diff patch + 完整文件

后端主动请求，非 Webhook 推送

4

上下文构建 + AI 分析

ContextBuilder 8K token 预算管理 → Stage 1 快模型 → Stage 2 四类并行深度分析

5

后处理 + DB 持久化

AST + AI 合并去重 → 置信度过滤 → 写入 Repository/PR/ReviewRecord/ReviewIssue 表

6

评论创建

DiffParser 解析 diff hunk → 行号映射 → 行级评论 + 总结报告 → 降级兜底

误报控制策略

企业场景下，误报比漏报更伤害信任。过多低质量建议导致评审者忽略所有 AI 评论。

1

置信度过滤

High ≥ 0.6
Medium ≥ 0.8
Low ≥ 0.9

2

去重合并

同文件 + 同 rule_id
+ 行范围重叠
保留高 confidence

3

忽略规则

文件 glob 模式
忽略规则 ID
类别开关

4

分级报告

Critical 必报
Warning 可选
Suggestion 默认关

设计理念：默认保守策略建立信任 → 用户可自行调高灵敏度 → 反馈闭环持续优化

上下文构建与 Token 预算

AI 模型的上下文窗口有限且昂贵 — 需要智能裁剪，只把关键信息喂给模型

Token 预算分配（8K 默认）

组件比例内容
🔍 Diff40%PR diff 文本 — 核心，不可压缩
🌳 AST20%结构信息 + 规则 findings
📄 文件20%变更行 ±50 行上下文
📦 项目10%依赖文件 · 配置文件
💾 缓冲10%预留空间，防截断

加载优先级

diff → AST 结构 → 文件内容 → 项目上下文

超限时按优先级裁剪，diff 不可压缩

智能截断

文件内容超过预算时，保留变更行周围上下文，其余部分省略标记

避免因 token 不足导致分析失败
