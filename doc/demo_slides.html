核心引擎：两阶段 AI 分析

为什么分两阶段？如果对每个 PR 都用最强模型全量分析，成本太高、延迟太大。先用快模型初筛，再用强模型针对性深度分析。

⚡ Stage 1 · 快模型

deepseek-v4-flash · 目标 < 10 秒

1

接收 PR 元信息 + diff + AST 结果

2

生成变更总结（中文/英文可配）

3

标记高风险文件 + 分析方向建议

4

输出 risk_level 评级（low/medium/high/critical）

🧠 Stage 2 · 强模型

deepseek-v4-pro · 四类别并行分析

🔒

Security 安全

SQL 注入 · XSS · 敏感信息泄露 · 权限绕过 · 不安全反序列化

🧩

Logic 逻辑

空指针 · 边界条件 · 异常处理 · 死锁风险 · 状态不一致

⚡

Performance 性能

N+1 查询 · 内存泄漏 · 阻塞 IO · 不必要对象创建 · 算法复杂度

🎨

Style 风格

命名规范 · 函数长度 · 圈复杂度 · 代码重复 · 最佳实践

AST 确定性规则引擎

AI 有幻觉风险，可能漏掉确定性安全问题。AST 做精确语法检测，AI 做上下文理解，两者互补。

GitHub Bot 评审全流程

从 PR 提交到评论创建，全自动 6 步链路

1

事件接收

PR opened / reopened / sync → GitHub 推送 Webhook → HMAC-SHA256 签名验证

2

数据拉取

通过 GitHub API 获取 PR diff、文件变更列表、完整文件内容、仓库结构

3

上下文构建

Token 预算管理（8K）→ diff 40% + AST 20% + 文件 20% + 项目 10% + 缓冲 10%

4

AI 分析

Stage 1 快速总结 → Stage 2 四类并行深度分析 → 结构化 JSON 输出

5

后处理

AST + AI 合并 → 同文件同规则去重 → 置信度过滤 → 忽略规则 → 排序

6

评论创建

Diff hunk 行号映射 → 行级评论 + 总结报告 → 异常降级为对话评论

手动 /review 命令

在 PR 评论区输入指令

  • /review — 全量分析
  • /review focus:security — 仅安全
  • /review focus:security,logic — 安全 + 逻辑
  • 权限校验：仅仓库协作者可触发

误报控制策略

企业场景下，误报比漏报更伤害信任。过多低质量建议导致评审者忽略所有 AI 评论。

1

置信度过滤

High ≥ 0.6
Medium ≥ 0.8
Low ≥ 0.9

2

去重合并

同文件 + 同 rule_id
+ 行范围重叠
保留高 confidence

3

忽略规则

文件 glob 模式
忽略规则 ID
类别开关

4

分级报告

Critical 必报
Warning 可选
Suggestion 默认关

设计理念：默认保守策略建立信任 → 用户可自行调高灵敏度 → 反馈闭环持续优化

上下文构建与 Token 预算

AI 模型的上下文窗口有限且昂贵 — 需要智能裁剪，只把关键信息喂给模型

Token 预算分配（8K 默认）

组件比例内容
🔍 Diff40%PR diff 文本 — 核心，不可压缩
🌳 AST20%结构信息 + 规则 findings
📄 文件20%变更行 ±50 行上下文
📦 项目10%依赖文件 · 配置文件
💾 缓冲10%预留空间，防截断

加载优先级

diff → AST 结构 → 文件内容 → 项目上下文

超限时按优先级裁剪，diff 不可压缩

智能截断

文件内容超过预算时，保留变更行周围上下文，其余部分省略标记

避免因 token 不足导致分析失败
